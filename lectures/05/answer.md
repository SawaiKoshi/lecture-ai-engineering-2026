- **検索だけを実行して見つかったページと、その本文で確認できたこと**：

  `uv run python -m app.retrieval "LoRA QLoRA 違い"`を実行したところ、第2回のPDF p.52、p.51、p.60、p.47、p.61の5ページが検索結果として表示された。

  特にp.52には、LoRAでは元の重みを固定して小さな行列A・Bだけを学習すること、QLoRAでは元の重みを4bitに量子化してメモリ使用量を削減することが記載されていた。p.51にも同様の説明があり、上位2件だけで質問に必要な根拠がそろっていた。

  一方、p.60やp.61は主に演習についての説明であり、質問に直接必要な根拠ではなかった。

- **`--trace`で見えたツール呼び出し（ツール名・引数・回数、Treeでたどった目次など）**：

  ベクトル検索では、`search_materials`が1回呼び出された。検索語は「LoRA 固定 QLoRA」だった。

  Treeでは`browse_tree`を使用し、第2回の「選んだモデルを、いつ・どう直すか」という章（`lec02-main-s045`）を開き、その後、LoRAとQLoRAについて説明しているp.52（`lec02-main-p052`）の全文を取得していた。モデル応答は5回だった。

  Graphでは`search_graph`が1回呼び出され、検索語は「LoRA 固定 学習 QLoRA 追加」だった。関連ページを取得し、それらを根拠に回答していた。

  全文投入では検索ツールを呼び出さず、227,971文字の資料を一度にモデルへ渡していた。

- **取得した情報が足りなかった例、取得できたのに回答へ使えなかった例**：

  全文投入では必要な根拠を含む資料が入力されていたものの、LoRAの学習対象やQLoRAの量子化について直接回答せず、ヒントを提示していた。一方、ベクトル検索とGraphでは必要な根拠を取得し、正しく回答できていた。

  今回確認した範囲では、検索結果から必要な根拠を取得できなかった例はなかった。

- **今回の用途に採用したい方式と、その理由・比較条件の限界**：

  今回のように講義資料から特定の用語について質問する用途では、基本RAG（ベクトル検索）を採用したい。

  今回確認した検索方式の中では、入力トークン数と推定費用が最も少なく、必要な根拠を取得して正しく回答できたためである。

  一方、Treeは目次をたどって対象ページを選べること、Graphは関連するページまで取得できることが特徴だった。ただし、各方式を1回ずつ試した結果であり、質問の種類によって結果が変わる可能性がある。また、全文投入と他の方式では対象資料の範囲が異なるため、今回の結果だけで方式全体の優劣は判断できない。

- **気づき・疑問**：

  同じ質問でも、検索方法によって回答時間やトークン数、費用が大きく異なることが分かった。特に、全文投入では大量の情報を渡したにもかかわらず、回答は一部がヒント形式となっていた。

  このことから、情報を多く渡せば必ず正確な回答が得られるわけではなく、必要な情報を効率的に取得することが重要だと感じた。複数ページにまたがる質問では、TreeやGraphの方が有効になる場合があるのか気になった。

## 宿題

- **取り組んだレベル**：基礎

- **やったこと（変更したファイル・設定・処理、または設計した取得方法）**：

  ただし、検索語は実行ごとに異なっており、設定値も実行ログに直接表示されないため、検索件数の変更だけによる効果と断定することはできない。

- **改善した例と、残る失敗・制約**：

  今回の質問では、検索件数が少ない実行でも必要な根拠が取得でき、回答の正確さを維持しながら入力トークン数や費用を削減できた。

  ただし、複数ページにまたがる質問では、検索件数を減らすことで必要な情報を取りこぼす可能性がある。また、1回ずつの実験では処理時間のばらつきも考えられるため、複数の質問や実行回数を増やした比較が必要だと考えた。

- **気づき・疑問**：

  検索件数を増やせば必ず回答の質が向上するわけではなく、質問に必要な情報を取得できていれば、少ない件数でも十分な場合があると分かった。

  実際にRAGを利用する際は、回答の正確さだけでなく、処理時間や費用とのバランスを考えて検索件数を設定することが重要だと感じた。また、質問の難しさや必要な根拠の数によって検索件数を自動調整できれば、さらに効率的になるのではないかと考えた。
